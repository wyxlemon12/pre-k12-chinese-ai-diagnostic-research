# 弘立 / CK STEM 面试展示型 Demo PRD

## 1. 文档目的

这不是正式产品 PRD，也不是后续项目实现的主规范。

这份文档服务于 `弘立书院 / CK STEM` 面试展示场景，目标是：

1. 用一份清晰、聚焦、可讲述的产品提案，体现我对岗位职责的理解。
2. 用 `2 天内可落地的 demo 范围` 展示我的产品判断，而不是做一个空泛的大平台。
3. 在不污染正式项目上下文的前提下，单独定义这次面试 demo 的功能边界、技术取舍和叙事方式。

本文件默认允许：

- 优先使用 `成熟商用 API` 提升 demo 质量
- 借用 `开源模块` 作为独立工具页或嵌入能力
- 只追求前端体验统一与 demo 可运行
- 尽量少改动借用项目的内部实现

本文件默认不承诺：

- 成本最优
- 全链路可控
- 全部能力自研
- 生产级合规落地

## 2. Why This Product, Why ISF / CK STEM

### 2.1 对弘立 / CK STEM 的理解

根据弘立官方公开资料与招聘信息，`CK STEM` 在学校体系中的角色不是单纯的技术支持部门，而是一个围绕：

- AI teaching and learning
- emerging technologies in curriculum
- industry partnerships
- future work capabilities

开展实验、研发与课程融合的创新平台。

这意味着面试作品不能只像一个“会聊天的中文 AI 工具”，而要像一个：

`能被中文教师真正拿去用、能融入学校课程设计、并体现教育理念的教学型应用。`

### 2.2 对弘立书院理念的理解

弘立 `Shuyuan` 强调：

- 中国书院传统与柏拉图式探究结合
- 在导师引导下进行独立研习与探究
- 跨学科学习
- 深层次思维
- 长期积累形成的学术训练

其精神可以压缩成四个动作：

1. `博学`
2. `慎思`
3. `明理`
4. `立言`

因此，这次 demo 不应只是帮助学生做对题，而应体现：

`系统如何在中文语境下，帮助教师设计探究路径，并帮助学生从理解走向推理与表达。`

## 3. 岗位映射结论

### 3.1 这份岗位真正看重什么

根据 JD，这个岗位不仅要求技术实现，更要求以下能力同时成立：

1. 与中文教师共同找出教学痛点并共创解决方案
2. 构建个性化、自适应的中文学习架构
3. 用 Python / LLM / 脚本自动生成分级中文学习材料
4. 能向教师解释并培训 AI 如何进入课堂设计与评估
5. 在隐私、文化完整性与课堂安全边界上有清晰判断

### 3.2 本 demo 对岗位的回应

本 demo 将产品定位为：

`一个面向香港国际学校中文教师的分层探究与苏格拉底式学习助手，用 AI 帮助教师快速设计课堂入口、生成中文特化追问链，并在课堂后形成可执行的教学建议。`

它重点回应岗位中的以下关键词：

- `Python + LLM API`
- `Pre K-12 / EdTech`
- `Chinese NLP`
- `teacher-friendly`
- `adaptive learning`
- `interactive learning`
- `SLA awareness`
- `Chinese culture and school ethos`

## 4. 产品主张

### 4.1 一句话主张

`这不是一个替学生答题的中文 AI，而是一个帮助教师做分层教学、帮助学生进行中文探究表达的教学助手。`

### 4.2 产品核心判断

1. 中文老师真正缺的不是更多内容，而是：
   - 如何给不同水平学生找到同一堂课的入口
   - 如何在课堂中追问到“刚好够难”
   - 如何在课后迅速判断“下一步该怎么教”
2. 对弘立语境而言，中文学习不能被做成机械 drill，而必须保留：
   - 文化语境
   - 表达层次
   - 探究路径
   - 教师主导权
3. 对面试 demo 而言，最佳策略不是做“大平台”，而是做一个：
   - 叙事清晰
   - 价值闭环完整
   - 技术路径可信
   - 可当场讲清楚的 sharp demo

## 5. Demo 设计原则

### 5.1 Teacher-first

AI 主要服务中文教师，而不是先服务学生聊天。

系统先帮助教师：

- 拆解课文
- 做分层
- 生成追问
- 调整支架
- 课后复盘

### 5.2 Chinese-specific

系统不是 generic tutor，而是围绕中文学习特性设计：

- 声调
- 普通话发音
- 汉字认读
- 词汇层级
- 句式表达
- 阅读理解
- 文化语境

### 5.3 Socratic, not answer-giving

系统以追问推进学习，而不是直接给答案。

学生体验按以下路径推进：

`理解 -> 推理 -> 表达 -> 立言`

### 5.4 Mixed-proficiency by design

默认一个班级中存在多种中文水平，因此产品必须支持：

- 同课异构入口
- 不同难度追问链
- 不同支架方式
- 不显性羞辱学生的分层表达

### 5.5 Human-in-the-loop

AI 只负责提出建议，不自动下结论。

教师始终保有：

- 审核权
- 编辑权
- 选择权
- 发布权

### 5.6 Demo-quality over system purity

这版 demo 优先追求：

- 体验质量
- 表达完整
- 现场演示稳定

不优先追求：

- 成本最小
- 能力全自研
- 后端架构最优雅

## 6. 2 天 Demo 范围

### 6.1 核心闭环

本次 demo 只做一个完整故事：

1. 教师输入一段中文课文或主题短文
2. 系统拆解出目标词、目标句、目标理解点
3. 系统生成 3 条分层入口
4. 系统为其中一个层级生成中文特化苏格拉底式追问链
5. 学生完成一轮互动
6. 教师看到课堂后建议：
   - 这个学生 / 这组学生目前卡在哪里
   - 下节课应该怎么调整支架

### 6.2 明确要做的页面

1. `教师首页 / Lesson Studio`
   - 输入课文或主题
   - 选择年段 / 学生类型
   - 生成课堂包

2. `分层结果页`
   - 显示 3 条路径
   - 每条路径显示目标学生、入口活动、支架方式

3. `追问链页`
   - 展示某一层级的中文追问步骤
   - 支持切换初级 / 中级 / 高级风格

4. `学生互动页`
   - 单轮或多轮苏格拉底式中文对话
   - 可以是文本或语音 + 文本混合

5. `教师反馈页`
   - 证据链
   - 薄弱点判断
   - 下节课建议

6. `工具页 / Tools`
   - 单独嵌入开源工具，例如笔画跟随、字形演示、朗读参考
   - 作为附加页面，而不是主流程核心

### 6.3 明确不做

- 完整 LMS
- 完整班级管理后台
- 家长报告
- 全套语音评测闭环
- 全学段课程适配
- 全自动高风险评分
- 复杂权限系统
- 长期成长档案

## 7. 功能确认

### 7.1 模块 A：教师共创式 Lesson Studio

功能目标：

- 让教师能快速把课文转成可执行课堂结构
- 体现“与中文教师合作找痛点并共同开发”的岗位要求

核心功能：

- 输入课文 / 粘贴教材片段 / 输入主题
- 选择班级特征：
  - 年级段
  - 母语 / heritage / 二语背景
  - 课堂目标
- AI 生成：
  - 本课三件套
  - 分层入口
  - 提问链草案
- 教师可直接修改与确认

产品价值：

- 体现 teacher-first
- 体现 co-creation
- 体现能把技术语言翻译成教师语言

### 7.2 模块 B：动态分层引擎

功能目标：

- 根据学生中文水平和课堂任务，生成不同入口与支架

demo 内的分层方式：

- `Level A 起步支持`
  - 图片、选项、词汇提示、句框
- `Level B 标准探究`
  - 基础阅读、原因追问、简单表达
- `Level C 延展表达`
  - 观点、比较、立场、文本关联

demo 中不做复杂全自动测评，而做：

- `规则 + 教师选择 + 轻量 AI 推荐`

动态分层规则只做表达，不做重实现：

- 如果学生连续完成词汇与理解任务，可升级追问抽象度
- 如果学生在词汇 / 发音 / 句式上卡住，则保留主题不变、降低表达负担
- 支架是局部调整，不做一次性贴等级标签

### 7.3 模块 C：中文特化苏格拉底追问引擎

功能目标：

- 把弘立书院“慎思、明理、立言”的精神转成中文课堂可用的追问链

追问设计按层级划分：

- `起步支持`
  - 看图命名
  - 二选一
  - 跟读 / 替换词
  - 句框补全

- `标准探究`
  - 为什么
  - 如果……会怎样
  - 你同意吗
  - 用“因为……所以……”说一句

- `延展表达`
  - 请给出理由
  - 换个角度理解
  - 和以前学过的内容比较
  - 如果你是作者 / 角色，你会怎样写

输出形式：

- 追问步骤
- 每一步的目标认知动作
- 可接受回答样例
- 教师提示语

### 7.4 模块 D：分级中文材料工作室

功能目标：

- 回应岗位中“提示工程与脚本撰写、自动生成符合等级的中文学习材料”的要求

demo 生成的材料类型：

- 分层阅读入口
- 目标词清单
- 句型练习
- 追问链
- 支架提示
- 课堂后建议

此模块不强调原创内容生成，而强调：

- 结构化生成
- 等级适配
- 教师可编辑
- 可导出用于课堂

### 7.5 模块 E：教师培训与上手提示卡

功能目标：

- 回应岗位中的“教师培训”要求

demo 中最轻量的实现方式：

- 在每个关键页面提供：
  - 这个结果是什么意思
  - 老师什么时候该采纳 AI 建议
  - 什么时候应该人工改写
  - 如何把结果带回真实课堂

具体形式：

- `How to use this` 卡片
- `课堂前 / 课堂中 / 课堂后` 3 步提示
- `AI 只是建议，不是结论` 的醒目说明

### 7.6 模块 F：工具页策略

功能目标：

- 借用成熟开源功能展示“更完整的中文学习支持”
- 不让这些工具拖慢主流程开发

适合工具页化的功能：

- 笔画跟随
- 字形拆解
- 朗读参考
- 拼音 / 声调练习小工具

处理原则：

- 作为独立 page 或 modal
- 前端样式统一
- 尽量不改原始功能逻辑
- 主流程只通过跳转、嵌入或轻封装调用

## 8. NLP / AI 能力与技术取舍

### 8.1 原则

这版 demo 优先考虑：

- 输出质量
- 中文效果
- 演示稳定性
- 集成速度

因此允许直接使用商用 API，而不是强行全自研。

### 8.2 建议的能力分配

#### A. LLM 编排与结构化输出

建议优先选择：

- `OpenAI compatible API`
- `MiniMax`
- `Claude compatible API`

适用任务：

- 课文拆解
- 分层入口生成
- 追问链生成
- 教师建议生成
- 教师培训提示卡生成

选择理由：

- 模型能力更稳
- 输出质量更高
- 更适合面试 demo 展示

#### B. 中文语音与发音能力

建议优先选择：

- `科大讯飞`
- 必要时辅以 `MiniMax` 的语音能力

适用任务：

- 普通话听写
- 朗读转文字
- 发音评测或评分展示

选择理由：

- 对中文教育场景更贴合
- 对普通话语音与评测表述更成熟
- 更利于展示“中文特化”而不是泛语音能力

#### C. 中文文本辅助能力

可选开源能力：

- `HanLP`
- `jieba`
- `pypinyin`

适用任务：

- 关键词抽取
- 句子切分
- 拼音 / 声调标注
- 结构化规则增强

选择理由：

- 适合作为轻量辅助层
- 可以为 LLM 输出提供 deterministic 支撑

### 8.3 Demo 推荐组合

若只以 `2 天 demo` 为目标，推荐组合为：

1. `LLM 主体`
   - 采用支持结构化输出的商用大模型 API
2. `中文语音`
   - 采用讯飞语音听写 / 评测能力
3. `规则增强`
   - 采用轻量中文 NLP 库
4. `开源工具页`
   - 采用现成笔画 / 字形 / 拼音练习类项目

## 9. 开源借用策略

### 9.1 策略目标

不是“证明所有东西都是我写的”，而是：

`证明我有能力把合适的能力组件组织成一个完整、可讲清楚、能跑起来的教育产品。`

### 9.2 使用原则

1. `主流程自己定义`
   - 教师工作流
   - 分层逻辑
   - 追问设计
   - 反馈结构

2. `工具能力外借`
   - 笔画演示
   - 字形辅助
   - 单点朗读演示

3. `尽量少改原项目内部逻辑`
   - 优先 iframe、页面嵌入、独立 route、轻包装
   - 避免深改依赖代码造成时间损耗

4. `前端统一`
   - 顶栏、配色、文案、页面壳统一
   - 保证用户感知是一个完整产品

### 9.3 适合外借而不适合主流程化的能力

- 笔画跟随
- 单字卡片工具
- 朗读示范
- 小型拼音对照器

## 10. 教师共创与审核机制

### 10.1 设计目标

回应岗位中的 `collaborative development` 要求。

系统不假设 AI 比老师更懂课堂，而是假设：

`AI 提供结构化初稿，教师进行专业判断。`

### 10.2 在 demo 中的体现

- 所有生成结果默认标记为 `建议稿`
- 教师可以：
  - 编辑
  - 删除
  - 替换
  - 确认
- 每个关键结果都附带：
  - 生成依据
  - 适合什么类型学生
  - 是否建议直接上课使用

### 10.3 未来可扩展方向

- 教师反馈回流
- 同年级共用模板
- 优秀追问链收藏与复用

## 11. Demo 版数据伦理与文化完整性框架

本章只写 `展示版治理框架`，不进入本轮代码实现。

### 11.1 数据伦理原则

1. `最小化数据使用`
   - demo 默认优先使用样例数据、匿名数据或临时输入
2. `教师确认优先`
   - AI 不自动做正式评价结论
3. `不做高风险标签化`
   - 不输出固定等级、能力排名、永久标签
4. `可关闭敏感功能`
   - 语音能力可选，不作为强制流程
5. `不把学生隐私当作产品素材`
   - 不以真实学生身份信息做展示

### 11.2 中文课程文化完整性原则

1. 中文学习不被简化成只有词汇 drill
2. 保留中文表达的语境、逻辑与文化意味
3. 支持学生从“会说”走向“会表达理由”
4. 保留教师对内容是否恰当、是否符合学校 ethos 的最终判断
5. 不把 AI 输出当作文化权威

### 11.3 面试中的表达方式

在面试中可明确说明：

- 这版 demo 只展示产品边界和课堂价值
- 合规与数据治理已提前建模
- 但不会在 demo 阶段伪装成生产级合规系统

## 12. 成功标准

如果这版 demo 成功，应满足以下标准：

1. 面试官能在 2-3 分钟内看懂产品在解决什么问题
2. 面试官能明确感受到这不是 generic tutor，而是：
   - 中文特化
   - 教师导向
   - 分层课堂导向
   - 与弘立 ethos 相符
3. 面试官能看出：
   - 我理解教师工作流
   - 我理解二语习得和混合起点课堂
   - 我能把商用 API、开源能力和产品设计组织成完整 demo
4. 面试官能自然联想到这套方案可以继续扩展到：
   - tonal recognition
   - stroke order
   - context-aware conversation

## 13. 面试时的讲述顺序

建议面试展示按以下顺序讲：

1. `先讲问题`
   - 香港国际学校中文课堂里，学生水平差异极大，老师难做同课分层
2. `再讲学校语境`
   - 弘立不是要一个刷题工具，而是要一个兼顾中文文化、探究精神和课堂落地的系统
3. `再讲产品判断`
   - teacher-first
   - Chinese-specific
   - Socratic
   - mixed-proficiency
4. `再讲 demo`
   - 课文输入
   - 分层入口
   - 追问链
   - 教师建议
5. `最后讲技术取舍`
   - 为了提高 demo 质量，允许商用 API 与开源能力混合
   - 主价值不在重复造轮子，而在产品组织与课堂适配
