# 6岁混合起点班级中文阅读与识字诊断助手设计稿

## 1. 产品定位

这是一个面向香港国际学校中文教师的课堂诊断助手，服务对象是 `6岁左右、混合起点` 的小学低年级学生。产品首版不负责大规模生成新阅读材料，而是帮助教师围绕已有课文、绘本片段或主题短文完成三件事：

1. 选出适合不同能力路径的材料入口。
2. 在一次课堂活动后快速判断学生卡点。
3. 给出下一步教学干预和下一篇材料建议。

首版锚定的课堂场景是：教师围绕一篇短文本组织一次 15-25 分钟的小组或全班活动，系统在活动前提供分层建议，在活动后提供诊断和跟进建议。为避免 6 岁儿童在单一任务中注意力流失，系统默认把一次活动拆成 3-4 个短节奏微活动，而不是一个连续长任务。

## 2. 目标用户与问题

### 2.1 核心用户

- 中文教师：主导选材、组织课堂、查看诊断、调整分组。
- 学生：6岁左右，处于中文学习起步阶段，同班存在中文家庭与非中文家庭混合起点。

### 2.2 需要解决的问题

- 同一班学生语言基础差异大，教师难以为一篇文本设计合适的分层入口。
- 教师知道学生“读不下来”，但难在课堂结束后迅速判断问题究竟出在词汇、认字、朗读输出还是理解。
- 现有教案已经存在，但课堂证据分散在观察、口头回答、朗读和工作纸中，难以沉淀为可操作的学习画像。
- 混合起点班级中，分层如果做得太显眼，容易让孩子感到“自己在弱组”，影响安全感与开口意愿。

## 3. 首版范围

### 3.1 首版诊断维度

首版只覆盖以下四个维度：

1. `听懂程度`
2. `认字与词汇`
3. `朗读与口语输出`
4. `阅读理解`

### 3.2 明确不做

- 不做开放式材料生成器。
- 不做完整自适应课程平台。
- 不做笔顺、书写和手写评测，这部分进入第二阶段。
- 不做高风险自动评分，不直接给学生贴“落后”标签。

## 4. 真实课堂蓝本

### 4.1 蓝本一：香港教育局《童心童趣》单元一《上学》教学设计

这份教学设计说明，6岁左右的中文课堂高度依赖以下活动链路：

- 教师引入个人经验。
- 学生观察图片并猜测人物心情与原因。
- 教师通过连续提问推动理解。
- 学生通过讨论、角色扮演和工作纸输出理解。

这说明首版产品必须支持 `看图说话`、`教师追问`、`角色活动后观察记录`，而不是只处理静态阅读题。

### 4.2 蓝本二：香港教育局小一《我的家》课册

这份课册更适合做产品首版样本课，因为它天然包含可结构化的任务链：

- 说一说自我信息
- 学句子
- 看图说话
- 课文阅读
- 理解题
- 词语分类与连线
- 高频字与部件识别

因此，首版产品以《我的家》这类短文本作为标准输入样本，并把工作纸视为核心诊断证据来源之一。

## 5. 课堂工作流

### 5.1 教师活动前

教师从以下两种入口之一开始：

1. 选择系统内置的样本课，例如《我的家》。
2. 上传或粘贴现有短文本、绘本片段或教案节选。

系统完成六步处理：

1. 抽取主题、核心词汇、关键汉字、句式、理解点。
2. 匹配知识图谱节点。
3. 为全班生成 2-3 个能力路径入口。
4. 输出本课三件套：目标词、目标句、目标理解点。
5. 生成提问梯度卡。
6. 生成工作纸映射表和关键观察点。

系统默认输出一个固定的微活动模板：

1. `3 分钟热身`
   - 看图、指认、说一个关键词
   - 必须包含一个可选择动作，例如选图、拿卡、圈一圈
2. `7 分钟核心阅读`
   - 教师带读或回声朗读，插入 2-3 个关键检查点
3. `5 分钟轻输出`
   - 指图、连线、选表情、句框补全、1 次短口头回应
4. `2 分钟收束`
   - 正向反馈、复盘 1 个重点、给教师记录本次观察点

每个微活动都要形成 `选择 + 完成 + 正向反馈` 的儿童侧小闭环，避免孩子感到“自己在被测试”。

### 5.2 教师活动中

教师在课堂中使用以下轻量功能：

- 查看每组建议任务与提问梯度卡。
- 以 `能力路径卡` 而不是公开的 A/B/C 分组组织活动，避免孩子感到被定级。
- 课堂中默认按 `小组` 或 `关键观察点` 记录，仅对 1-3 名需要重点跟进的学生补充个人备注。

首版分层在教师端保留能力差异，但在学生端显示为中性路径名，例如：

- `故事探索卡`
- `词语侦探卡`
- `分享小达人卡`

这些路径允许在同一节课中流动切换，不形成固定等级。

系统同时提供 `无设备课堂包`，供教师一键导出为可打印或可投影材料，默认包含：

- 路径卡
- 提问梯度卡
- 关键观察点打点表
- 工作纸映射摘要

课堂中教师可以完全不盯设备，课后再把纸笔或投影使用结果回填系统。

### 5.3 教师活动后

系统产出：

1. 每个学生在四个维度上的本次课堂表现摘要。
2. 每个小组的共性卡点。
3. 下次教学建议：
   - 继续阅读什么类型的文本
   - 该补哪些词汇、字形或句型
   - 适合做全班重教还是小组补救
4. 工作纸和课堂问题的错因映射摘要。

## 6. 知识图谱骨架

首版只构建够用的小型知识图谱，节点分为六类：

1. `主题词汇`
   - 家人、食物、日常活动、学校、身体、颜色、动物
2. `核心汉字`
   - 高频基础字，例如《我的家》中的 爸、妈、哥、家、女、米、不
3. `字形结构`
   - 全包围、左右结构、上下结构、常见部件
4. `字音与声调`
   - 容易混淆的音节与声调
5. `句型功能`
   - 自我介绍、喜好表达、并列、否定、简单描述
6. `阅读理解点`
   - 找人物、找地点、找事实、顺序、简单因果、情绪理解

节点之间的关系只保留教学上最有价值的几种：

- `文本 -> 覆盖 -> 词汇/汉字/句型/理解点`
- `学生表现 -> 暴露 -> 薄弱节点`
- `薄弱节点 -> 推荐 -> 跟进活动或下一篇材料`

知识图谱主要在系统内部使用。教师端默认不展示复杂图谱结构，而是展示 `本课三件套`：

1. `目标词`
2. `目标句`
3. `目标理解点`

教师只在需要时查看更详细的节点来源和推荐逻辑。

## 7. 核心模块

### 7.1 教案与文本解析模块

输入教师提供的文本、绘本页摘要或教案片段，输出：

- 主题
- 核心词汇表
- 关键汉字表
- 句型表
- 理解问题点
- 推荐活动类型
- 课内工作纸或口头任务的证据点

目标不是“重写教案”，而是把已有材料拆解成可诊断结构。

### 7.2 分层选材模块

围绕同一主题和文本，为教师生成三类入口：

- `路径一：起步支持`
  - 图片支持、词汇预教、句框、同伴支援、单句理解
- `路径二：标准课堂`
  - 按原文本完成阅读和理解
- `路径三：延展表达`
  - 复述、比较、个人经验连接、简短原因说明

该模块的核心输出是“怎么进这节课”，不是“自动写一篇新课文”。教师端同时看到每条路径对应的支架策略，避免分层只剩“简单版/困难版”。

三条路径在学生端应保持 `相同界面结构、相近任务长度、相近视觉形式`，差异主要体现在隐藏支架上，例如：

- 更多图片支持
- 更少干扰项
- 可重复播放音频
- 句框提示
- 更明确的两选一或三选一任务

### 7.3 提问梯度卡模块

系统为每篇文本生成一组 `提问梯度卡`，直接贴合真实课堂追问方式。每张卡包含：

- `观察性问题`
- `推论性问题`
- `证据性问题`
- `评价或连接性问题`
- `低门槛可接受回答`
- `升级追问`

例如围绕《我的家》，系统应能区分：

- 找人物和地点
- 说出谁喜欢什么
- 用文本证据解释“为什么哥哥叫开心果”

这样诊断结果能回溯到具体问题，而不是停留在抽象归因。

### 7.4 课堂观察记录模块

教师可在课堂中快速点选课堂表现标签，避免重输入。首版默认 `按小组` 记录，课后再允许补充个体。

首版标签建议固定为：

- 听懂但不回应
- 需要图片提示
- 核心词汇不稳
- 认字犹豫
- 朗读不顺
- 声调影响理解
- 只会找事实
- 能解释原因

每节课系统预先生成 6-10 个高信息量观察点，教师只需标记：

- 达成
- 部分达成
- 未达成

允许教师补一条自由备注，但不要求大量录入。课堂中推荐每组只做 1-2 次点击，剩余记录在活动后完成。

### 7.5 工作纸与任务映射模块

首版把《我的家》这类课册后的工作纸和练习题作为核心证据来源之一。

系统需要把每道题映射到：

- 所属诊断维度
- 目标词/句/理解点
- 常见错因
- 可执行补救动作

例如：

- `圈一圈填一填`
  - 重点看事实提取、词汇理解、专名干扰
- `想一想`
  - 重点看原因解释和情绪理解
- `连一连`
  - 重点看词义分类和视觉识别

### 7.6 诊断与归因模块

系统结合文本难点、课堂标签和教师备注，给出低风险归因：

- 主要困难更像是词汇问题、认字问题、口头输出问题或理解问题。
- 诊断只用于教学建议，不做正式评价结论。
- 诊断结果必须能追溯到课堂证据，例如某个提问梯度卡、工作纸题目或课堂观察点。

首版的诊断输出强制采用 `证据链三段式`：

1. `证据`
   - 来自哪一道工作纸题、哪一张提问梯度卡或哪一个观察点
2. `推断`
   - 落到四个诊断维度中的哪一个困难
3. `下一步动作`
   - 对应支架方式，以及下次建议调整的提问或活动

### 7.7 下一步建议模块

对教师输出三类建议：

1. `学生级`
   - 下次优先补哪些词、字或句型
2. `小组级`
   - 哪个组适合继续当前文本，哪个组需要换更短、更有图像支持的文本
3. `班级级`
   - 是否值得在下一节课全班重教某个句型或词汇簇

建议同时包含明确的 `支架方式`，例如：

- 图片词卡
- 句框
- 同伴复述
- 排序卡
- 选图回答
- 表情卡

## 8. 儿童体验与安全规则

首版必须遵守以下儿童侧规则：

1. 每个活动段落都要有“我能完成”的低门槛回应方式。
2. 原因解释类任务必须提供支架，例如表情卡、图片选择、句框，而不只要求完整口头表达。
3. 差异化路径不能在学生侧显式呈现“高低等级”。
4. 错误反馈以提示和重试为主，优先私下修正，不在全班前放大。
5. 每次活动必须以一次成功体验或正向反馈结束。
6. 每个原因解释类检查点都必须提供一个 `非口头成功路径`，例如：
   - 表情卡
   - 选图指证
   - 单词填空句框
   - 因为/所以 二选一配对

## 9. 输入与输出

### 9.1 输入

- 一篇现成短文本或课册页面
- 教师上传的简短教案片段
- 教师在课堂中的标签式观察
- 教师在关键问题点上的达成记录
- 教师用轻量模板勾选的目标词、目标句和关键理解点
- 可选的学生基本背景：
  - 中文家庭/非中文家庭
  - 近期已学主题

### 9.2 输出

- 分层入口建议
- 本课三件套：目标词、目标句、目标理解点
- 提问梯度卡
- 工作纸映射表
- 课堂观察摘要
- 学生/小组/班级建议
- 下一篇材料推荐条件，而非直接生成全文

## 10. 材料库边界

首版不承诺开放互联网检索式推荐，而是建立一个 `20-40 篇` 的可控小型文本库，来源包括：

- 香港教育局公开课册页
- 公开教学设计中的文本片段
- 适合低年级的自建短文本样本

每篇材料提前标注：

- 目标词
- 目标句
- 目标理解点
- 推荐活动类型
- 推荐适用路径

这样推荐结果更稳定，也更适合 demo 展示。

对于自定义文本或自制工作纸，首版提供一个 `3 分钟轻量配置模板`。教师只需完成：

- 勾选目标词，最多 10 个
- 勾选目标句，最多 2 个
- 勾选关键理解点，最多 3 个
- 从预置观察点库中选择 6-10 个观察点

这样可以让产品从样本课扩展到更多真实备课场景，而不要求老师做大量手工标注。

## 11. 数据与安全边界

- 首版使用匿名或合成学生数据。
- 不存储敏感音视频原件作为必需能力，朗读记录首版先以教师勾选观察代替。
- AI 输出不可直接发布给学生，需教师确认。
- 系统不生成“能力排名”或固定标签，只输出可修改的教学建议。
- 对非中文家庭学生，允许教师选择是否开启 `英语词义或图像双支架`，但该支架只作为进入文本的辅助，不替代中文输出目标。
- 公开仓库中的案例材料以公开链接、引用说明和结构化摘要为主，不直接分发受版权限制的绘本全文或图像内容。

## 12. 成功标准

如果首版有效，应至少满足以下标准：

1. 教师能在 5 分钟内把一篇文本转成可执行的分层课堂活动。
2. 教师能在一次课堂后快速看出学生主要卡在哪一个维度。
3. 教师愿意基于系统建议调整下一次分组或选材。
4. Demo 展示时，能清楚体现“不是生成器，而是教师诊断与选材助手”。

## 13. 第二阶段

第二阶段再扩展：

- 笔顺与书写
- 学生朗读音频分析
- 更长期的个人成长轨迹
- 更多主题和绘本的知识图谱

## 14. 技术选型与系统架构

### 14.1 选型原则

首版技术方案遵循四个原则：

1. `教师优先`
   - 首版重点是教师工作流和课堂可用性，不为了炫技增加复杂技术。
2. `快迭代 + 可解释`
   - 研究型 demo 需要快速调整规则、提示词、结构化输出，因此核心业务逻辑应保持高可改性。
3. `中文语言处理友好`
   - 需要方便接入 LLM、分词、规则抽取、文本解析与知识图谱处理。
4. `关键能力可逐步性能化`
   - 先用 Python 跑通，性能或本地化要求更高的部分再下沉到 Rust。

### 14.2 总体技术栈

- 前端：`React`
- 后端主服务：`Python`
- 高性能与本地处理模块：`Rust`
- 数据层：首版可用 `SQLite/Postgres`，后续再接 `Supabase/Postgres`
- 模型接口层：`OpenAI / Claude 兼容 API`，保留本地模型适配口

### 14.3 前端：React 的职责

React 负责所有教师端和演示端交互界面，重点包括：

- 教师文本导入页
- 本课三件套展示页
- 提问梯度卡查看页
- 路径卡与支架策略页
- 工作纸映射与错因归因页
- 课堂后诊断摘要页
- 无设备课堂包导出页

选择 React 的原因：

- 适合快速搭建教师工作台和结构化信息界面。
- 组件化强，适合把“路径卡”“提问卡”“证据链卡片”做成可复用 UI。
- 后续如果要做公开作品集站点、demo 视频页和交互原型，也可以共用同一套前端工程。

前端建议采用：

- `React + TypeScript`
- 样式：`Tailwind CSS`
- 状态管理：先用 React 原生状态和轻量 store，不急着上复杂状态框架
- 导出能力：浏览器端 PDF/打印样式 + 服务端生成课堂包

### 14.4 后端主服务：Python 的职责

Python 作为首版主后端，负责高迭代速度的核心业务逻辑：

- 文本解析与教案拆解
- 目标词、目标句、目标理解点抽取
- 提问梯度卡生成
- 工作纸题目映射
- 课堂观察点配置
- 证据链三段式诊断生成
- 知识图谱节点与关系管理
- LLM prompt orchestration
- 管理公开材料元数据与推荐逻辑

选择 Python 的原因：

- 与 NLP、LLM、教育研究型原型最匹配。
- 容易接入规则、提示词、结构化 JSON 输出。
- 后续如果要加入中文文本难度分析、简单分类器、embedding 检索，生态成熟。
- 岗位要求里也明确提到了 Python，这对求职作品集是加分项。

后端框架建议：

- API：`FastAPI`
- 数据校验：`Pydantic`
- 后台任务：首版可先同步处理，后续有需要再上 `Celery / RQ / Dramatiq`

### 14.5 Rust 的职责

Rust 不作为首版主业务开发语言，而是承担“值得性能化和本地化”的模块：

- 中文文本规则匹配与高速预处理
- 课堂包导出或批量结构化处理中的高性能任务
- 后续音频处理、朗读特征提取、离线评分前处理
- 需要本地运行、低延迟或更强安全隔离的解析组件

选择 Rust 的原因：

- 适合把后续重 CPU、重并发、重安全的部分独立成稳定模块。
- 可作为 Python 扩展模块或独立微服务接入。
- 作为作品集，也能体现你不仅会“调 API”，还考虑到了系统性能与本地部署路线。

首版对 Rust 的具体落点建议收敛到两个可展示方向：

1. `文本预处理引擎`
   - 负责高频字、结构标签、规则特征的快速抽取
2. `课堂包生成器`
   - 负责把结构化 lesson plan 数据转换为导出文件或离线包

### 14.6 模块边界

推荐按以下边界拆分：

1. `React 前端`
   - 只负责交互、表单、结果展示、导出触发
2. `Python Orchestrator`
   - 负责核心业务流程、LLM 编排、诊断逻辑、知识图谱和推荐
3. `Rust Engine`
   - 负责可性能化的规则处理或导出任务
4. `Database`
   - 负责材料元数据、课次记录、观察点配置、学生匿名画像

这样拆分的好处是：

- 首版可以几乎只靠 React + Python 跑通
- Rust 能作为亮点逐步接入，而不是一开始把系统复杂度拉满
- 后续无论迁移到学校内部部署还是上云，都还有演进空间

### 14.7 API 设计建议

前后端之间建议保持结构化 API，而不是自由文本接口。首版可以定义以下核心接口：

- `POST /lessons/parse`
  - 输入文本或教案片段，输出本课三件套
- `POST /lessons/pathways`
  - 输出 2-3 条能力路径及支架建议
- `POST /lessons/question-ladders`
  - 输出提问梯度卡
- `POST /worksheets/map`
  - 输出题目到诊断维度的映射
- `POST /observations/diagnose`
  - 输入观察点与工作纸结果，输出证据链三段式诊断
- `GET /materials/recommend`
  - 输出下一篇材料建议
- `POST /lesson-packs/export`
  - 导出无设备课堂包

### 14.8 数据模型建议

首版核心实体可以控制在以下几类：

- `Material`
  - 文本、来源、主题、目标词、目标句、目标理解点、推荐路径
- `LessonPlan`
  - 本课输入、提问梯度卡、路径卡、观察点配置
- `WorksheetItem`
  - 题目内容、题型、诊断维度、常见错因、补救动作
- `ObservationRecord`
  - 小组或学生层观察结果
- `StudentProfile`
  - 匿名化维度画像与历史建议
- `Recommendation`
  - 下一步支架、下一篇材料和全班重教建议

### 14.9 首版推荐架构

如果我们把“求职 demo 能跑通、能讲清楚”作为第一优先级，我建议首版采用：

- 前端：`React + TypeScript + Tailwind`
- 后端：`FastAPI + Pydantic`
- 数据库：`SQLite` 本地开发，保留切换到 `Postgres` 的能力
- Rust：先实现一个小型 `text-preprocess` 或 `lesson-pack-export` 模块

这个组合最平衡：

- 足够快，能尽快做出 demo
- 足够工程化，能体现你不是只会做 prompt demo
- 足够可演进，后续可以自然扩成学校内实际系统

### 14.10 为什么这套选型适合岗位申请

这套架构正好能映射岗位需求：

- `Python`
  - 对应 AI/ML 集成、LLM 编排、内容与诊断逻辑

  - 对应教师友好型应用界面与可演示产品能力
